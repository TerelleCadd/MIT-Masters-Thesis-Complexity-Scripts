# Wildfire System-of-Systems Modeling Framework

## Overview
This repository contains MATLAB-based tools for modeling wildfire response as a System-of-Systems (SoS). The framework links architecture design (via Design Structure Matrices, DSMs) to both system complexity and operational performance.

The workflow integrates:
- DSM-based architecture definition
- Complexity quantification (C1, C2, C3)
- Wildfire spread and suppression simulation
- Detection delay modeling (including optional STK integration)
- Large-scale architecture trade studies
- Post-processing and trade space visualization

The primary objective is to evaluate tradeoffs between **system complexity** and **wildfire response performance** across different scenarios and architectures.

---

## Required Setup (Google API Key)

Before running the wildfire performance model, you must provide a valid Google Maps API key.

This is required for:
- Downloading map imagery
- Aligning wildfire perimeters
- Running the fire spread simulation

### Setup Steps
1. Create a Google Cloud account  
2. Enable the Google Static Maps API  
3. Generate an API key  
4. Replace the key in the main driver script:

```matlab
perfCfg.apiKey = "YOUR_API_KEY_HERE";
```

If this is not configured, the wildfire simulation will fail.

## Repository Workflow

The repository is organized into three main stages:

1. **Single Architecture Evaluation**
   - Defined and executed in `main_driver.m`

2. **Architecture Sweeps / Trade Studies**
   - Executed in `sweep_driver.m`

3. **Trade Space Visualization and Analysis**
   - Performed in `final_comparison_plots.m`

Each stage builds on the outputs of the previous one.

---

## Main Driver: `main_driver.m`

### Purpose
This script evaluates a **single wildfire response architecture** from start to finish.

### Key Functions
- Loads DSM data from Excel
- Allows user to configure architecture via GUI
- Applies scenario presets (e.g., Butte County, Etosha, US/Canada)
- Expands architecture based on multiplicity
- Computes system complexity:
  - C1 (element complexity)
  - C2 (interface complexity)
  - C3 (topological complexity)
- Runs wildfire performance simulation
- Outputs results to Excel

### Workflow
1. Load DSM and element definitions
2. Select included elements and multiplicities
3. Expand DSM into full architecture
4. Compute complexity metrics
5. Run wildfire simulation
6. Output performance and complexity results

### Output
- Expanded DSM matrix
- Interface count tables
- Complexity values
- Performance results (Excel)

---

## Sweep Driver: `sweep_driver.m`

### Purpose
This script performs **large-scale trade studies** across many architectures.

### Key Functions
- Generates many architecture configurations
- Varies:
  - Asset counts
  - Organizational structure
  - System composition
- Runs the wildfire performance model for each configuration
- Stores results in `.mat` files

### Workflow
1. Define parameter ranges (assets, organizations, etc.)
2. Iterate through architecture combinations
3. For each configuration:
   - Build architecture
   - Compute complexity
   - Run wildfire performance simulation
4. Store results in matrix `R`
5. Save results to `.mat` file

### Output
- `.mat` files containing:
  - Performance metrics
  - Complexity values
  - Scenario metadata

Example outputs:
- `sweep_results_final_butte_county.mat`
- `sweep_results_final_etosha_national_park.mat`
- `sweep_results_final_us_canadian_wildfires_usgov.mat`

These files are required for post-processing and plotting.

## Final Plotting Script: `final_comparison_plots.m`

### Purpose
This script performs **post-processing and visualization** of trade study results.

### Requirement
This script requires that `.mat` files generated by `sweep_driver.m` are already present in the working directory.

If these files are not available, the script will not run.

### Key Functions
- Loads sweep result matrix `R`
- Filters invalid architectures
- Computes utility using AHP-weighted metrics
- Identifies Pareto-optimal architectures
- Generates trade space visualizations

### Utility Calculation

Utility is computed as a weighted combination of normalized performance metrics:

- Resolution Time
- Burn Burden (AUC)
- Total Cost
- CO2 Emissions

Each metric is normalized using robust percentile scaling:

```
U = (P95 - x) / (P95 - P5)
```

Total utility:

```
Utility = w1*U_resolution
        + w2*U_burn
        + w3*U_cost
        + w4*U_CO2
```

Weights are scenario-specific and derived using AHP.

### Plots Generated
- Complexity vs CO2
- Complexity vs Resolution Time
- Complexity vs Burn Burden
- Complexity vs Cost
- Complexity vs Utility
- Utility vs Complexity (colored by burn burden)
- 3D performance trade space
- 3D utility–complexity–burn burden plots
- Utility component breakdown
- Parallel coordinates plots
- Cross-scenario comparisons
- Utility difference plots

### Output
- MATLAB figures
- Workspace variables for further analysis
- No modification of original `.mat` files

## Key Concepts

### Complexity
- **C1**: Element complexity
- **C2**: Interface complexity
- **C3**: Topological complexity

Total complexity:

```
C = C1 + C2 * C3
```

---

### Performance Metrics
- Resolution time
- Burn burden (area under curve)
- CO2 emissions
- Detection delay sensitivity

---

### Detection Delay Modeling
The framework evaluates:
- Immediate response
- Fixed delays (e.g., 2–12 hours)
- Satellite-driven detection delays

Early delays significantly increase fire growth and overall impact.
